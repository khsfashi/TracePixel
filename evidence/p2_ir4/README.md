# P2-IR4 IR compactness / replay / invalidity evidence

This directory is the preregistered P2 engineering checkpoint from `docs/BENCHMARK.md`.
It is development evidence, not a scored B0 product claim.

## Fixed visible fixture set

The checkpoint uses three deterministic 16x16 fixtures:

- `potion-16` — the same recognizable potion shape introduced in P1-R3,
- `gem-16`,
- `key-16`.

Each fixture starts from a transparent canvas and records only non-transparent pixel edits.

## Compared representations

Three measurements are recorded for each fixture.

1. **Canonical PixelProgram v1** — the actual `tracepixel.pixel-program.v1` canonical UTF-8 JSON emitted by `serialize_pixel_program`.
2. **Raw primitive call stream** — a deliberately compact engineering baseline with one `set_pixel` call per pixel edit. This is not a production schema; it represents the lower-level tool-call surface that batched Pixel IR is intended to avoid.
3. **Bare edit-array JSON** — only the compact `[x,y,r,g,b,a]` arrays, with no schema/canvas/operation context. This is a lower-bound payload reference, not independently replayable program state.

The rough token proxy is `ceil(UTF-8 bytes / 4)` for each serialized form. It is explicitly **not** an actual provider tokenizer count.

## Frozen result

`structural.json` is generated by `python -m evidence.p2_ir4.benchmark`.

Across the three fixtures:

| Metric | PixelProgram v1 | Raw primitive | Bare edits |
|---|---:|---:|---:|
| UTF-8 bytes | 5,545 | 8,269 | 5,188 |
| rough token proxy | 1,388 | 2,069 | 1,298 |
| calls / public operations | 3 | 250 | n/a |

The v1 program is 2,724 bytes smaller than the compact one-call-per-pixel primitive stream while requiring 3 public operations instead of 250 primitive calls. Its self-describing schema/canvas/operation envelope adds only 357 bytes over the context-free bare edit arrays across the three fixtures.

All three PixelProgram replays match the corresponding direct `Canvas.set_pixel` primitive replay exactly.

## Invalidity evidence

The checkpoint exercises every current P2 semantic validation code:

- `invalid_type`
- `invalid_fields`
- `unsupported_schema`
- `invalid_canvas`
- `unsupported_operation`
- `invalid_edit`
- `invalid_coordinate`
- `invalid_color`

It also records the two IR3 wire-level serialization failures: `invalid_type` and `invalid_json`.

The committed evidence requires the expected stable code/path to be observed. No live provider, tokenizer, image dependency, GPU, secret, or self-hosted runner is needed.

## Operation-vocabulary decision

P2-IR4 does **not** add another public operation.

`set_pixels` remains the sole `PixelProgram v1` operation because the fixed visible set:

- expresses every edit required by the fixtures,
- replays exactly,
- collapses 250 primitive calls to 3 batched public operations,
- stays close to the bare edit-array lower bound,
- and provides no measured evidence that line/rectangle/fill or art-aware convenience operations would reduce the current P2 concept budget enough to justify overlapping authority.

This is not a claim that `set_pixels` must be the only operation forever. Later staged-authoring workloads may justify an intentional versioned addition, but such an addition must come with measured complexity benefit rather than convenience alone.
